연결 풀, DB 작업자, JSON 응답, 추적과 커널 설정은 유지합니다.
게임 v57의 apply-update.py를 적용한 경우 서버 도구는 ZIP을 덮어써두면 됩니다.
이전 서버 도구의 --apply는 사용하지 마세요.

게임 실행 구조/DB 저장 방식/연결 풀 크기를 바꾸지 않습니다. --apply나 서버 재시작은 필요 없습니다.

v3 변경 / 2026-11-02
최근 v10 시험에서 앱 시각까지 확인된 실패 486건은 모두 새 백엔드 연결의 첫 요청이었습니다.
실패 요청의 Nginx 시작→앱 수신 중앙값은 약 5.92초였습니다. 이 관찰만으로 TCP 내부 원인이 확정된 것은 아닙니다.
cluster의 소켓 전달 대신 경량 HTTP 프록시가 게임 프로세스 1개에 최대 64개의 연결을 재사용합니다.
외부 포트는 3000을 유지하며 게임은 컨테이너 내부 127.0.0.1:3001에 바인딩합니다.
계정/방/게임 상태는 계속 게임 프로세스 1개가 소유합니다. DB 데이터/점수 규칙은 변경하지 않습니다.
PC 요청량, 사용 인원, 5초 제한은 유지합니다. 연결 풀 대기도 기존 요청 시간에 포함됩니다.
Server-Timing의 proxy_queue와 POP_RUSH_PROXY_TRACE/POP_RUSH_POOL_STATS로 풀 대기를 구분합니다.
수집/분석에는 공개 3000과 내부 3001 수신 대기열을 함께 표시합니다.
Nginx 연결 대상이나 커널 설정을 추가로 바꾸지 않습니다.
--apply 중 pool 단계에서 컨테이너를 재시작하므로 진행 중인 경기가 없는 때 적용하세요.
실패 시 해당 단계의 두 실행 파일을 백업에서 복원합니다. 복구 명령도 출력합니다.

검증 결과:
- 로컬 실제 API: 800명/100방/5초, 7,862건 실패0. 조회 p95 472ms, move p95 76ms.
- 96개 동시 요청에서 64개 연결 제한과 대기 시간 표시, 쿠키/보안 헤더, 대기 중 취소,
  백엔드 연결 실패 502 처리 및 이후 정상 요청, 정상 종료 확인.
- 적용/이미 적용됨/수동 복구/재시작 실패 자동 복구 확인(Docker 명령 모의).
- 추적 활성 실제 API: 100명/13방/5초 947건 실패0, 요청 ID/메타데이터 왕복 확인.
로컬 통과는 대상 AWS에서의 성능 보증이 아닙니다. 같은 Windows v12 시험으로 비교해야 합니다.

수집 중 Ctrl+C를 눌러도 ZIP 저장 완료를 기다리는 v2 보완을 유지합니다.
PC에서 시험이 끝난 뒤 서버 수집 창에서 Ctrl+C를 한 번 누르면 저장이 시작됩니다.

POP RUSH 통합 서버 업데이트 v4 / 고정 파일명 POP_RUSH_Server_Update.zip

앞으로 서버 수정/진단 도구는 이 ZIP과 이 폴더, update.py 명령으로 유지합니다.
과거에 제공한 Accept/DBWorker/JSON/Payload/Request_Trace 적용/수집 코드를 modules 폴더로 통합했습니다.
이번 버전은 백엔드 연결 전달 경로를 재사용 연결 풀로 바꿉니다. 이미 반영된 수정은 건너뜁니다.
이전 폴더와 백업/로그는 자동으로 삭제하지 않습니다.

업로드 /home/ubuntu 후:
 cd /home/ubuntu
 unzip -o POP_RUSH_Server_Update.zip
 cd /home/ubuntu/POP_RUSH_Server_Update
 sudo -n python3 update.py --apply

인자 없이 실행하면 현재 상태만 확인합니다.
--apply는 accept → db → json → payload → pool → trace 중 누락된 단계만 적용합니다.
누락 단계가 있으면 해당 단계에서 컨테이너를 재시작합니다. 진행 중인 경기가 없는 때 실행하세요.
모두 적용돼 있으면 재시작하지 않습니다. 각 단계별 검사 실패 시 그 단계를 복원하고 중단합니다.
앞서 완료된 단계까지 전체 일괄 롤백하지는 않습니다. 각 단계의 복구 명령은 출력합니다.
대기열 설정은 자동 변경하지 않습니다. 별도 --backlog 옵션은 기존 도구가 필요한 경우에만 사용합니다.

수집은 항상 같은 명령:
 sudo -n python3 update.py --collect --seconds 300
요청 ID 왕복 확인 완료 후 Windows v12으로 시험하세요. GUI는 서버의 요청 ID 응답이 없으면 부하 시작 전 중단합니다.
윈도우 창에서 POP_RUSH_LOADTEST_VERSION=12 표시와 FILE 경로를 확인하세요.
서버 결과는 POP_RUSH_Server_Update/logs 아래에 저장됩니다. 새 서버 ZIP/이번 Windows TXT를 함께 전달하세요.
수집 결과는 시험 구분을 위해 날짜/시간을 유지합니다. 배포 파일명은 고정입니다.

복구:
 sudo -n python3 update.py --restore 단계명 백업경로
단계명: accept, db, json, payload, pool, trace, backlog. 실제 명령은 각 단계 적용 시 출력합니다.
DB 데이터/게임 규칙을 바꾸지 않는 기존 보완을 통합한 것이며 800명 통과를 보장하지 않습니다.

검증: 이미 적용된 단계 모두 건너뛰기, 하위 모듈 Python 구문, 기존 각 모듈의 기능/복구 검증.
Docker/Nginx 실제 적용은 대상 서버에서 검사합니다.
동봉 Windows v12은 로컬 실제 API 100명/13방/5초 956건 실패0, 요청 ID 왕복 일치.
추적 미준비 상태에서는 사전 확인 요청 1건만 보내고 게스트/방 생성과 측정 요청은 0건임을 검증했습니다.
